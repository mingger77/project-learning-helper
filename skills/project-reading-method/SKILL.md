# project-reading-method（项目阅读方法论）

目标：先给项目定档，再按档位阅读，最后把事实转成「可教」的表达，支撑 TEACHER.md 与 STUDENT.md。

## 一、判断项目大小

**判定原则**：**以模块数/业务复杂度为核心依据，行数作为兜底参考**。先看"有多少个模块、多少条业务链路、多少个入口"，再看行数是否与判断相符；两者矛盾时，以复杂度为准。

**复杂度判据（核心）**：

1. **顶层模块数**：顶层源码目录/包的数量（排除生成物与第三方），如 `src/core`、`src/services`、`src/utils` 各算一个模块。
2. **入口数**：入口文件/可执行目标/服务进程（main、CLI、web 服务、worker、脚本命令）数量。
3. **业务链路数**：README 或代码中呈现的功能点/命令/能力清单数量（一条"输入→处理→输出"链路）。
4. **扩展点数量**：插件/SPI/注册点/配置驱动的可扩展处（有明确扩展点通常意味着"大型"）。
5. **辅助特征**：目录深度、依赖规模、是否有 CI/构建体系、是否多仓库/多服务。

**行数兜底（参考锚点）**：自有代码总行数（含测试；排除 node_modules/dist/build/out/vendor/缓存/.git/锁文件/二进制/转译产物）；当复杂度判断模糊时用行数校验归属。

**五档判定标准**：

| 档位 | 复杂度判据（核心依据） | 行数兜底（参考） | 参考锚点 |
|---|---|---|---|
| 微型 | 1 个模块、≤1 个入口、1 条链路、无构建体系 | ≤ 200 行 | 单文件或少于 200 行；一个脚本 |
| 小型 | 1~3 个模块、1 个入口、1~3 条链路、无/极简构建 | ≤ 2,000 行 | 单模块 CLI/小工具库 |
| 中型 | 4~10 个模块、1~2 个入口、4~10 条链路、有配置与构建 | ≤ 20,000 行 | 单服务 web 应用/常规库 |
| 大型 | 11~50 个模块、多入口/多服务、有插件或扩展点、有 CI | ≤ 200,000 行 | 框架/多模块应用 |
| 巨型 | >50 个模块、多仓库/多服务/超大规模 | > 200,000 行 | 参考 llama.cpp |

**判定动作**：读取 README/顶层目录/清单文件做快速判法（顶层模块数、入口数、功能点、行数）→ 按上表归档 → 在 TEACHER.md §0/§1 写明**判据与理由**（如"11 个模块、3 个入口、8 条功能链路，判为大型；兜底行数 42k 与判断相符"）。

**量测命令**（辅助，用于行数兜底）：

```bash
# 优先：cloc（若已安装），--exclude-dir 排除生成物
cloc . --exclude-dir=node_modules,dist,build,out,vendor,.git

# 次选 A：git 仓库内统计（干净、可复现）
git ls-files | grep -vE '^(node_modules|dist|build|out|vendor)/' | xargs wc -l | tail -1

# 次选 B：PowerShell 下快速统计
Get-ChildItem -Recurse -File | Where-Object { $_.FullName -notmatch '\\(node_modules|dist|build|out|vendor|\.git)\\' } | Measure-Object -Property Length -Sum
```

## 二、五档阅读策略

> 共性约定：结论可追溯（path:line）；只读（`learning_plan/` 唯一可写）；运行验证命令前说明用途；每档都要写明"完成了什么、没覆盖什么"，不把抽样说成全量。

| 档位 | 策略 | 承诺 |
|---|---|---|
| 微型 | **全量精读（一次性）**：100% 文件通读（含入口），可即时运行验证；读完全部产出 | 全部结论可追溯；无未覆盖项（或明确列出） |
| 小型 | **全量精读（1 轮会话内完成）**：主干（入口→配置→核心→存储）→支线（工具/测试/文档）→运行 1 条验证命令 | 全部结论可追溯；未运行验证的命令逐条标注 |
| 中型 | **主干精读 + 外围抽样（2~4 轮，可中断续读）**：五轮法全流程；主干 100%；外围抽样 ≥30% 并搜索求证；外围可交子代理并行 | 主干 100% 可追溯；外围注明"抽样自哪些文件"；未读列入 TEACHER.md §8 |
| 大型 | **分层抽样 + 委托（多轮，建议子代理）**：先建地图 → 与用户确认目标挂靠 → 核心子系统按"中型"精读、其余按目录抽样+搜索求证 → 独立模块委托子代理 | 主干 100% + 目标子系统 100%、其余抽样覆盖；未读/未验证清单逐项列出 |
| 巨型 | **导航式阅读**：**必须先与用户确认目标子系统**，否则不开始深读；建全局地图 → 圈定目标子系统 → 该子系统按"大型"策略深读 → 标题注明范围 | 明确输出"部分地图"；全局导航 + 目标子系统 100%；其余只给导航卡片；建议多会话/多 Agent 接力 |

## 三、导演式阅读五轮法

### 第 0 轮：项目名片（快速）

只读项目门面：README；文档目录（docs/、ADR、CHANGELOG）；依赖清单（package.json / pyproject.toml / go.mod / Cargo.toml / pom.xml 等）；入口文件（main / index / __main__ / app）；构建与测试脚本、CI 配置。

产物：「项目卡片」——名称与一句话定位、语言/运行时/框架、构建与测试命令（标注已验证/未验证）、入口与关键依赖、自解释文档清单、版本/许可 + 档位判据。

### 第 1 轮：骨架沙盘

沿真实执行路径只读主干——入口 → 配置/初始化 → 核心处理 → 存储/副作用（持久化、网络、输出）。不深入每条分支；先拿到「一句话叙事」（输入 → 处理 → 输出）。

产物：一句话叙事 + 分层骨架图（ASCII/Mermaid）+ 骨架调用链（入口到最外层副作用）。

### 第 2 轮：三透镜测绘（平行采集证据）

- **结构透镜**：目录树逐目录标注职责；识别模块边界与依赖方向（import/require/include/using）；排除生成物与第三方。产物：带注释目录树 + 模块-职责表 + 模块依赖方向图。
- **动态透镜（数据流）**：从入口沿调用链追踪数据的产生、变换、传递与落地；识别输入源与输出汇（文件、DB、网络、消息队列、事件）；每条端到端流给出证据链，错误路径单独记录。产物：端到端数据流图（每节点 文件::符号）+ 每条流证据链 + 输入源/输出汇清单。
- **状态透镜（状态机）**：搜显式状态机（状态枚举/常量、状态字段、转换函数/表、事件触发、状态监听）；搜隐式状态（状态住在对象字段/DB 列/文件内容/标志位/配置开关；谁写它、什么事件驱动转换）。产物：状态表（状态含义+所在符号）+ 迁移表（源态/事件/动作/目标态）+ 触发源清单。

### 第 3 轮：提问先行深挖

先列「学习者会问的问题」，再到代码中找答案：

- 为什么这样设计（取舍）；如果 X 会怎样（边界）；改这里影响谁（耦合）；最小可运行示例怎么做（验证）。
- 深挖设计动机：读注释、提交历史、ADR；记录明显取舍（事件 vs 直接调用、同步 vs 异步、单例 vs 注入等）。
- 读错误路径：异常层级、重试/回退、日志、失败模式。
- 扫历史包袱：TODO/FIXME/HACK/迁移/兼容层；记录「为什么现在长这样」的线索。

产物：问题→答案（带证据）清单；设计动机与取舍要点；错误处理剖面；历史包袱清单。

### 第 4 轮：教学化转写（橡胶鸭）

把事实转成「可教」的表达：

- 对每个核心子系统/概念做四段自述：一句话 + 代码示例（真实符号）+ 为什么这样 + 常见误解。
- 确定学习路径：新读者按什么顺序读哪些文件（入口→核心→外围），每阶段写「你将学会什么」。
- 设计练习：基于真实扩展点/入口的动手任务（易到难），给提示与验证方式。

产物：概念-教学卡片集；推荐阅读路径；练习集（与 STUDENT.md §7 一一对应）。

## 工具使用提示

- 结构/搜索：glob、grep；阅读：read（带行号，便于引用证据）。
- 验证命令需用户同意；默认只读（`learning_plan/` 除外）。
- 用 `todo_write` 跟踪轮次；完成每轮可给用户一句进展。
